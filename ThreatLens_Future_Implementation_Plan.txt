THREATLENS - FUTURE IMPLEMENTATION PLAN
Approval Draft
Date: 2026-09-30

PURPOSE
This document proposes how to turn the current ThreatLens prototype into a
Windows desktop product without adding a local SQL database and without
showing invented scan data. This is a plan for approval; it does not authorize
the next implementation phase by itself.

CURRENT STATE
- The app is a Flet desktop UI that launches the C++ Phase 1 scanner.
- Phase 1 returns real target, DNS, subdomain, host, and TCP port/service data.
- Python currently keeps scan history in process memory. Closing the app loses
  that history.
- The GUI can build scanner_gui.exe at runtime, which currently requires GCC.
- Findings, endpoints, web crawling, TLS/header/cookie analysis, and technology
  detection do not have connected providers. Those screens must remain empty or
  say NOT CONNECTED until real results exist.

RECOMMENDED STORAGE: NO LOCAL DATABASE
Use ordinary versioned JSON files, not SQLite or another local database.

Windows data directory:
  %LOCALAPPDATA%\ThreatLens\

Suggested layout:
  settings.json                 User preferences
  scans\<scan-id>.json          One immutable JSON result per completed scan
  reports\                      User-exported TXT, HTML, PDF, or JSON files
  evidence\                     Real evidence files only, when a provider exists

Write scan files atomically: write a temporary file, flush it, then rename it
to the final scan ID. Rebuild the history list by reading scan JSON files at
startup. Add schema_version to every stored document so later versions can
migrate formats safely. Provide export/backup and delete controls.

Why this fits now:
- No database installation, service, credentials, or schema administration.
- Works offline and is easy for a single-user desktop app to back up.
- Human-inspectable and compatible with the scanner's existing JSON output.
- Not intended for simultaneous multi-user writes or team synchronization.

If multi-device or team sync is needed later, add an optional authenticated
HTTPS API with server-side storage. Keep that separate from the offline default;
do not silently upload scan results.

SIMPLER USER FLOW
Keep only four primary navigation destinations visible:
  1. Dashboard
  2. Scan
  3. Targets
  4. Reports

Move Findings, Endpoints, Technologies, Network, Evidence, History, and
individual tools under a collapsible Advanced section. Show an Advanced page
only when it has real data or mark it clearly as NOT CONNECTED.

Recommended scan flow:
  1. Enter URL/domain and confirm authorization.
  2. Choose Quick or Standard. Put custom wordlists and full TCP range under
     Advanced Options; keep full-range confirmation explicit.
  3. Review scope, then Start Scan.
  4. Show one results overview with DNS, subdomains, hosts, ports, and export.

Do not show fake progress, severity counts, example targets, or success banners.
The current scanner does not stream live progress or produce vulnerability
findings; show completed results or a truthful unavailable/empty state.

IMPLEMENTATION ROADMAP

Phase A - Reliable offline session data
- Save each successful scanner JSON result under the LocalAppData path above.
- Restore Targets, Scan History, Reports, and latest result at app startup.
- Derive counts from stored scanner records; keep Findings as N/A until a real
  finding engine supplies them.
- Add safe delete, export, and backup behavior for stored records.

Phase B - Reduce the interface
- Keep the four primary destinations visible and move specialist pages under
  Advanced.
- Use one simple Quick/Standard scan path; place wordlist, timeout, workers,
  custom ports, and full-range controls under Advanced Options.
- Preserve clear authorization and full-range confirmations.
- Show unavailable backend modules without example output.

Phase C - Windows packaging
- Build the Flet app using the installed Flet Windows build workflow
  (flet build windows) after confirming Flutter and Windows build prerequisites.
- Compile scanner_gui.exe during release/build, not on the user's computer.
- Bundle scanner_gui.exe and the required MinGW runtime DLLs as app resources.
- Resolve the bundled scanner path from the installed app; do not depend on
  C:\ThreatLens or an installed GCC path.
- Test on a clean Windows machine with no Python, virtual environment, or GCC.
- Add version metadata, app icon, installer/update strategy, and code signing
  decision before public distribution.

Phase D - Future backend modules (separate approval)
- Web discovery: bounded crawler, URL/API extraction, scope enforcement.
- HTTP/TLS/header/cookie checks: real requests, timeouts, evidence capture.
- Technology detection: evidence-backed fingerprints and confidence.
- Findings: versioned checks, severity rationale, remediation, and evidence.
- Each module must output structured data; the UI must never synthesize results.

BACKEND CONTRACT
Keep the current process boundary:
  Flet UI -> Python scan coordinator -> bundled C++ scanner -> JSON result

Python responsibilities:
- Validate user settings and authorization confirmation.
- Start/stop the child process where supported and collect errors.
- Validate the JSON schema, add local scan metadata, persist the result.
- Refresh views from saved real scan files.

C++ responsibilities:
- Continue producing one machine-readable JSON document on stdout.
- Keep scanner implementation independent from Flet and UI rendering.
- Never emit progress/log text into stdout when JSON mode is requested; use
  stderr for diagnostics.

ACCEPTANCE CHECKLIST
- Fresh Windows installation starts without Python or GCC installed.
- A permitted test target creates one persistent JSON scan record.
- Closing and reopening restores that scan in Targets, History, and Reports.
- Report exports contain the exact real scan data and no fabricated findings.
- Unimplemented pages display empty/unavailable states, not sample content.
- Default scan remains conservative; full TCP range requires confirmation.
- No scan data leaves the computer unless the user explicitly enables a future
  remote-sync feature.

DECISIONS REQUESTED
Please approve or change these four choices before the next coding phase:
1. JSON files under %LOCALAPPDATA%\ThreatLens instead of a local database.
2. Four primary navigation destinations, with specialist pages under Advanced.
3. Bundle a prebuilt scanner_gui.exe and runtime DLLs in the Windows release.
4. Keep unconnected features empty; add each real provider in a later phase.
